## 0. 한눈에 보는 결론

**기준서의 뼈대(원칙 · 데이터 모델 · 4층 시뮬 · 블록 체계)는 유지할 가치가 높습니다.** 같은 문제를 푸는 기존 도구들(Visual Components, Siemens Process Simulate / Plant Simulation, FlexSim, realvirtual, Omniverse)과 비교해도, "웹에서, 블록으로, 신호 테이블 하나로" 가는 방향은 비어 있는 자리를 정확히 노리고 있습니다. 통째로 대체할 만한 더 좋은 방법은 없습니다.

다만 **꼭 고쳐야 할 것 5가지**가 있습니다.

| # | 문제 | 왜 중요한가 | 제안 |
|---|------|-------------|------|
| 1 | **일정이 안 맞음**: 기준서 본문은 "전담 11주", 부속 기능 로드맵 엑셀은 "약 4~5개월(19~22주)" | 같은 문서 묶음 안에서 2배 차이. 11주는 혼자 + AI 보조로 53개 기능을 만들기엔 비현실적 | 일정을 **16~20주**로 잡거나, V1에서 최적화 루프(9~10주차)를 V1.5로 빼서 11주를 지킴 |
| 2 | **시퀀스(설비 동작 순서) 모델이 약함**: "간이 스텝 에디터"만 있음 | 설비 사람은 PLC의 SFC(순차 기능 차트)를 압니다. 간이 스텝으로는 분기·병렬·인터록을 못 그려 L2 재현이 막힘 | **IEC 61131-3 SFC**를 시퀀스 모델로 채택. 화면은 단순하게, 데이터는 표준대로 |
| 3 | **버전이 1~2년 뒤처짐**: Node 22, Fastify 4, Vite 5, React 18, three r16x | 지금 시작하는 프로젝트가 처음부터 구버전이면 1년 뒤 마이그레이션 비용 | Node 24 LTS, Fastify 5, Vite 7, React 19 + r3f 9, three r18x. WebGL2 유지, WebGPU는 V2 |
| 4 | **SharedArrayBuffer의 숨은 조건** | 신호 테이블을 SAB로 하려면 사이트 전체에 COOP/COEP 헤더가 필요하고, 그러면 외부 iframe·일부 CDN이 막힘 | V1은 `postMessage` + `Transferable`로 시작, SAB는 성능 측정 뒤 결정 |
| 5 | **서버 부품이 V1치고 많음**: PostgreSQL + Redis + BullMQ + MinIO + Python 서비스 2개 + Nginx | 혼자 운영하기엔 무겁고, 첫 고객 전에는 쓰이지 않는 부품이 절반 | V1은 PostgreSQL 하나로 큐까지(pg-boss), Redis는 세션·실시간이 필요해질 때 |

그리고 **바꾸지 말아야 할 것**: 원칙 1·2·4·5·8(단일 모델, 신호 테이블, 편집 API, 블록=형식, 외부는 변환), 4층 시뮬 구조, mm·deg·Z-up 규약, realvirtual 코드 금지.

## 1. 검토 방법

- **효율성**: 같은 결과를 더 적은 코드·사람·돈으로 낼 수 있는가
- **대체 가능성**: 기존 상용/오픈소스 도구나 다른 기술로 바꾸면 더 나은가
- **위험**: 나중에 바꾸기 어려운 결정인가, 숨은 조건이 있는가
- **일관성**: 기준서 본문과 부속 엑셀, 우리 다른 문서가 서로 맞는가

다섯 역할([08](08_ROLES.md))이 각자 관점에서 봤습니다. MR은 제품·범위·일정, RS는 시뮬·로봇, OT는 신호·현장, TA는 3D·블록, PD는 화면·사용성.

## 3. 설계 원칙 8개 검토

| # | 원칙 | 판정 | 근거 · 대안 |
|---|------|------|-------------|
| 1 | 단일 데이터 모델 (노드 트리 ECS JSON) | **유지** | 모든 실시간 3D 편집기(게임 엔진, Omniverse USD, realvirtual)가 같은 구조. 대안인 "모듈별 별도 모델"은 반드시 동기화 버그를 낳음 |
| 2 | 신호 테이블 단일 통신 | **유지 + 보강** | 시뮬과 현장이 같은 구조라는 점은 이 제품의 핵심. 보강: 태그에 **품질(quality)·타임스탬프**를 처음부터 넣을 것 (OPC UA가 그렇게 함). 안 넣으면 V2 현장 연결 때 스키마가 바뀜 |
| 3 | fidelity L1/L2/L3 혼재 | **유지** | Visual Components도 "간이/상세" 혼재. 좋은 결정 |
| 4 | 편집 API 레이어 | **유지** | AI·MCP·테스트·Undo가 전부 이 위에 올라감. 가장 투자 대비 효과 큰 원칙 |
| 5 | 블록은 형식, 제품이 아니다 | **유지** | 카탈로그 경쟁(Visual Components 수천 개)에서 벗어나는 유일한 길. 단, 치수 테이블 검증(verified)은 꼭 지켜야 신뢰가 남음 |
| 6 | spec 섹션 null 허용 | **유지** | 비용 거의 없음, 나중에 큰 이득 |
| 7 | 서버 분리 | **보류 → 단계화** | 방향은 맞지만 V1 첫날부터 전부 서버일 필요는 없음. 엔진이 같은 코드라면 V1은 브라우저에서 돌리고 "보호가 필요한 것"(치수 테이블·최적화)만 서버로 시작. 아래 5장 |
| 8 | 외부 플랫폼은 변환으로만 | **유지** | USD나 AAS를 저장 형식으로 삼는 대안은 둘 다 브라우저 편집기에 부적합(아래 6장) |

"자체 개발 금지 항목"(물리·프로토콜 변환·ROS2 브리지·STEP·영상)은 **전부 타당**합니다.

## 4. 시스템 구성 (브라우저 / 서버 / 현장 3층)

**대안 A: 전부 서버 스트리밍** (Omniverse 웹 뷰어처럼 GPU 서버에서 그려서 영상으로 보냄)
- 장점: 브라우저가 약해도 됨, 코드 보호 완벽
- 단점: 고객 1명당 GPU 서버 1대. 중소기업 가격에 못 맞춤. **기각.** V3에서 로봇 셀 정밀 물리만 이 방식으로 붙이는 건 가능

**대안 B: 로컬 우선(local-first)** (브라우저에만 저장, 서버는 동기화만)
- 장점: 서버가 거의 없음, 오프라인 가능
- 단점: 블록 라이브러리 보호 불가, 협업 어려움. **기각.** 단, "브라우저에서 돌아가는 데모 시뮬"은 이미 기준서에 있으므로 V1 초반엔 사실상 로컬 우선처럼 개발하고 서버는 저장·인증부터 붙이면 됨

**대안 C: 3층 유지하되 V1 서버를 최소화** → **채택 제안**
- V1 서버: 저장(PostgreSQL JSONB) + 인증 + 블록 라이브러리 전달 + 정식 시뮬 큐 1개
- 미루는 것: Redis, MinIO(S3는 클라우드 S3 직접), Prometheus/Grafana, Nginx(Caddy나 클라우드 LB), 변환 서비스는 DXF 하나만(STEP·USD·AAS는 V2라 어차피 없음)

**판정: 보강(단계화).** 구조도는 유지하고 10장 일정에 "서버 부품 도입 시점"을 적어 넣습니다.

## 5. 기술 스택 항목별

| 계층 | 기준서 | 판정 | 검토 내용 |
|------|--------|------|-----------|
| 언어 | TS 5 strict, Python 3.12 | **유지** | 표준. Python 3.13도 가능하나 pythonocc 호환은 3.12가 안전 |
| 저장소 | pnpm + Turborepo 모노레포 | **유지** | 패키지 경계(schema·engine·blocks)가 이 제품의 핵심 구조. 대안 Nx는 더 무거움. **단, 기존 `BSE_STUDIO/apps/web`가 이미 pnpm인지, Vite인지 먼저 확인**(D-23) |
| 프론트 | React 18, Vite 5, React Router | **교체(버전)** | 2026-11 현재 React 19 + Vite 7이 현역. r3f 9가 React 19 전용. 지금 18로 시작하면 1년 안에 올려야 함 |
| 3D 렌더 | Three.js r16x, r3f 8, drei | **교체(버전) + 유지(선택)** | three는 r186(2026-09)까지 나옴. r3f 9 + drei 최신. **WebGL2 기본은 유지**가 맞음: WebGPU는 Chrome·Edge·Safari 26·Firefox에서 켜져 있고 "대부분 프로젝트에 production ready"지만 Linux 부분 지원이고 "모든 장면에서 더 빠르진 않음". V1은 `WebGLRenderer`, V2에서 `three/webgpu`(WebGL2 자동 폴백)로 전환 검토. **대안 Babylon.js**: WebGPU가 더 앞서 있고 옥트리·인스펙터 내장이지만 번들 1MB+, r3f 같은 React 생태계 없음, CAD 로더 강점은 우리가 STEP을 서버에서 변환하므로 무의미. **Three.js 유지** |
| 3D 보조 | three-mesh-bvh, Draco, KTX2, urdf-loader | **유지 + 보강** | 보강: 파라미터→메쉬 생성에 **three-bvh-csg**(불리언 연산) 또는 자체 프리미티브 조합. 블록 지오메트리 함수 50개를 손으로 짜는 것이 2~4주차 최대 병목이므로 **CSG 조합기로 통일**하면 절반으로 줄어듦 |
| 상태 | zustand + immer, zundo, TanStack Query | **유지 + 메모** | 적절. 메모: V3 멀티유저(보류 등급)를 염두에 두면 노드 트리를 **Yjs(CRDT)** 위에 올리는 길이 열려 있어야 함. 지금 할 일은 아니고, "노드 id가 안정적이고 트리 조작이 명령 단위"라는 현재 설계가 이미 그 조건을 만족 |
| 스키마 | zod → JSON Schema | **유지** | zod 4 기준. 편집 명령도 zod에서 생성하는 설계는 좋음 |
| UI | Tailwind, Radix, lucide, i18next | **유지** | shadcn/ui(= Tailwind + Radix)를 쓰면 더 빠름. 한국어 기본 OK |
| 시뮬 (브라우저) | Web Worker + Comlink + **SharedArrayBuffer** | **보류(SAB)** | SAB는 `Cross-Origin-Opener-Policy`/`Embedder-Policy` 헤더가 사이트 전체에 필요. 그러면 외부 iframe(지도·영상·결제), 헤더 없는 CDN 이미지가 막힘. **V1은 Worker + postMessage(Transferable ArrayBuffer)**로 시작. 태그 수천 개 × 10ms면 postMessage로도 충분. 병목이 측정되면 SAB로 |
| 시뮬 (서버) | 같은 엔진을 Node Worker Threads, BullMQ | **보강** | 큐는 **pg-boss**(PostgreSQL 기반)로 시작하면 Redis가 필요 없음. 동시 시뮬 수십 건까지 충분. 수백 건 병렬(최적화 루프)이 되면 BullMQ로 교체 가능하도록 큐 인터페이스를 얇게 |
| DES | 자체 이벤트 스케줄러, seedrandom | **유지** | JS DES 라이브러리(simjs, simscript, typesim)는 유지보수가 약하고 신호 테이블과 결합이 안 됨. 자체 구현이 맞음(핵심은 300줄 내외). 결정적 시드는 필수 |
| 네비 | 격자·그래프 A* 자체 | **유지** | 바닥 마킹 → 그래프가 입력이므로 navmesh 불필요. 다중 AMR 충돌은 V2 |
| 로봇 IK (V2) | closed-chain-ik 또는 자체 | **유지** | closed-chain-ik(MIT, urdf-loader 저자)가 Three.js 생태계와 맞음 |
| 물리 (V3) | MuJoCo WASM, Isaac Sim | **보강** | 브라우저 접촉 물리는 **Rapier**(Rust→WASM, r3f용 `@react-three/rapier` 있음)가 통합이 쉬움. MuJoCo WASM은 로봇 정밀도가 높지만 Three.js 결합을 직접 해야 함. "셀 단위 물리"는 Rapier로 먼저 보고, 로봇 학습 연동 때 MuJoCo/Isaac |
| 최적화 | pymoo, Optuna | **유지 + 메모** | 레이아웃 최적화는 조합 문제라 **OR-Tools**(CP-SAT)가 더 맞는 경우가 있음. V1은 GA로 "보이는 최적화"를 만들고, 정확한 해가 필요할 때 OR-Tools 추가 |
| AI (V2) | Claude API, MCP SDK | **유지** | 편집 API가 있으면 MCP 노출은 얇음. 그대로 |
| 백엔드 | Node 22, Fastify 4 | **교체(버전)** | Node 24 LTS(2028-04까지), Fastify 5. Node 26도 2026-10 LTS 예정 |
| DB | PostgreSQL 16, Drizzle | **유지** | 17도 가능. JSONB 1행 + 버전 테이블 설계 좋음 |

## 6. 데이터 모델

### 6.1 대안 비교
| 대안 | 평가 |
|------|------|
| **USD를 저장 형식으로** | 브라우저용 USD 런타임이 없음(2026-11 현재 Needle 등 일부 변환 뷰어만). 편집·Undo·스키마 검증을 전부 다시 만들어야 함. **기각**. 내보내기로 충분 |
| **AAS를 저장 형식으로** | AAS는 "설비 정보 교환" 표준이지 3D 장면·관절·시뮬 상태 모델이 아님. 억지로 넣으면 서브모델이 비대해짐. **기각**. 변환이 맞음(D-22) |
| **glTF 확장에 메타데이터** (realvirtual 방식) | 한 파일 전달엔 편하지만, 편집 중 데이터가 지오메트리에 묶여 diff·버전·참조 인스턴스가 어려움. **기각**. 단, "공유용 GLB에 카드 요약을 extras로 넣기"는 V2 공유 뷰어에서 써도 됨 |
| **SysML v2 / AutomationML** | 설비 엔지니어링 교환 표준. 중소기업 사용자에겐 과함. **기각**, V3 이후 내보내기 후보 |
| **자체 ECS JSON (기준서)** | 편집기에 최적. **채택** |

### 6.2 보강할 점 (R2 후보)
1. **태그에 quality·timestamp 필드** (원칙 2 보강). 지금은 값만 있음
2. **단위 명시**: 파일 머리에 `"units": {"length": "mm", "angle": "deg"}`. 변환기와 외부 도구가 추측하지 않게
3. **스키마 버전 + 마이그레이션 규칙**은 있는데 **마이그레이션 테스트 세트**(옛 파일 → 새 스키마)를 11주차 회귀에 포함
4. **참조 인스턴스의 버전 고정** `machine@version`은 좋음. 라이브러리 블록도 `blockType@version`으로 고정해야 치수 테이블이 바뀌어도 옛 설비가 안 깨짐
5. **시퀀스**: `"sequence": {"steps": []}`를 **SFC**(IEC 61131-3 Sequential Function Chart: 스텝·전이·동작·분기·병렬)로. 설비 제작사가 이미 아는 그림이고, V2 "실PLC 태그 녹화"와 자연스럽게 이어짐. 화면은 세로 스텝 목록으로 단순하게 시작해도 데이터는 SFC로
6. **바이너리 첨부 규약**: 레퍼런스 이미지·glb는 S3 키 참조만, JSON에 base64 금지

## 9. 범위와 일정

### 9.1 일정 불일치
- 기준서 10장: **전담 11주**, 병행 시 22주

같은 묶음 안에서 두 숫자가 다릅니다. 엑셀 쪽(19주)이 모듈별로 쪼개져 있어 더 믿을 만합니다. 혼자 + AI 보조 + 오너 검수 하루 1~2시간이면 **16~20주**가 현실적입니다.
