## 1. 한눈에 보기

- 기준서는 **"브라우저에서 설비와 공장을 3D로 만들고, PLC 신호로 돌려 보고, 결과를 비교·최적화하는 웹 디지털 트윈"**을 11주 안에 V1으로 만드는 설계도입니다.
- 지금 우리 문서(00–09)는 **방향과 랜딩 페이지** 중심이고, 기준서는 **실제 제품을 어떻게 만들지** 중심입니다. 그래서 대부분은 충돌이 아니라 **빈칸을 채우는 관계**입니다.
- 다만 **크게 다른 곳이 4군데** 있어서, 오너가 먼저 정해 주셔야 문서를 고칠 수 있습니다 (아래 2장).
- 랜딩 사이트는 **거의 그대로** 둡니다. 기준서는 랜딩이 아니라 그 뒤에 있는 빌더 앱의 기준입니다.

## 2. 먼저 오너가 정할 것 (4가지)

기준서와 지금 문서가 정면으로 다른 곳입니다. 이게 정해져야 나머지 정리를 시작할 수 있습니다.

### 결정 1. 제품 이름: 초안의 이름 vs "BSE : Digital Twin"
- 초안: 다른 제품명과 주소를 씀.
- 지금: 제품명 **BSE : Digital Twin** (D-01), 주소 `bse-digital-twin.vercel.app`.
- 선택지
  - **A (추천)**: 초안의 이름을 제품명으로, BSE는 그 안의 작업 흐름 이름(Build · Simulate · Execute)으로 둔다. 랜딩은 당분간 그대로.
  - B: 전부 초안의 이름으로 바꾼다 (랜딩 제목·로고 설명·문서 전체 수정).
  - C: BSE : Digital Twin을 유지하고 초안의 이름을 우리 이름으로 바꿔 읽는다. **(오너 선택)**

### 결정 2. 시뮬레이션의 중심: 웹 자체 엔진 vs Omniverse/Isaac
- 기준서: 시뮬레이션은 **웹에서 돌아가는 자체 엔진**(신호 → 동작 → 물류 흐름 → 이동 경로, 4단계). 물리 엔진은 직접 만들지 않고, Isaac/MuJoCo는 **V3(나중)**에 로봇 셀에만.
- 지금(03 아키텍처, 08 역할 RS): Omniverse/Isaac Sim이 시뮬레이션의 중심, OpenUSD로 주고받기.
- **추천**: 기준서를 따른다. Omniverse/Isaac은 "V3 정밀 물리·로봇 학습"으로 자리를 옮기고, RS 역할의 지금 일은 "자체 엔진의 동작 속도·사이클타임 계산 검수"로 바꾼다.

### 결정 3. 설비 정보 표준: AAS/AASX vs 기준서의 machine.json
- 기준서: 설비·공장을 **자체 JSON 형식**(machine.json / factory.json) 하나로 저장. AAS는 언급이 없음.
- 지금(01·02·03·07): 설비 정보는 AAS/AASX로 붙인다 (B-03).
- **추천**: 저장 형식은 기준서의 JSON. AAS는 "내보내기/가져오기 변환" 기능으로 V2 이후 후보로 내림 (기능 로드맵에 등급 달아 백로그로).

### 결정 4. 기존 BSE Studio 앱과의 관계
- 기준서: 새 저장소 구조(pnpm 모노레포 `apps/web`, `apps/api`, `packages/schema` 등)로 처음부터.
- 지금: `BSE_STUDIO/apps/web` (내 컴퓨터, localhost:5173)가 원래 빌더 앱이고, **건드리지 않기로** 되어 있음.
- 선택지
  - **A (추천)**: 기존 앱은 참고용으로 그대로 두고, 기준서 구조로 **새 저장소**를 만든다. 쓸 만한 화면 코드는 옮겨 온다.
  - B: 기존 앱을 기준서 구조로 고쳐 나간다 (기존 앱을 수정해야 하므로 지금 규칙과 충돌).
- 어느 쪽이든 새 GitHub 저장소는 오너가 직접 만들어 주셔야 합니다 (Claude는 저장소를 새로 만들 수 없음).

## 4. 적용 순서

### 1단계. 오너 결정 받기 (하루)
- 2장의 결정 4개를 정합니다. 정해지는 대로 06 결정 기록에 D-19 ~ D-22로 남깁니다.
- 함께 정할 것: "**기준서와 우리 문서가 다르면 기준서를 따른다**"는 원칙 (D-23 제안).

### 2단계. 문서 정리 (1~2일, 코드 변경 없음)
기준서를 그대로 베끼지 않고, 우리 문서는 **쉬운 설명 + 기준서 몇 장을 보라는 링크**로 둡니다. 한 내용은 한 곳에서만 "주"로 다룬다는 00번 규칙을 지킵니다.

1. 원본 보관: `docs/standard/` 폴더에 기준서 docx와 엑셀 4개를 넣습니다. 고치지 않고 원본 그대로.
2. **00 문서 지도**: 10번(이 계획서)과 `standard/` 폴더 추가. "제품 개발의 최종 기준 = 기준서 R1" 한 줄.
3. **01 개요**: 대상 고객, 하지 않는 것, 성공 기준을 기준서 1장·9.2절로 교체. 모듈 대응표(B/S/E ↔ 머신빌더/팩토리빌더/시뮬레이션) 추가.
4. **02 요구사항**: 2.2~2.4의 "(제안)" 기능표를 기준서 9.1절 V1 범위(공통·머신빌더·팩토리빌더·시뮬레이션)로 교체. 랜딩(2.1)은 그대로. P0/P1/P2 대신 기준서의 V1/V2/V3 + 등급 사용.
5. **03 아키텍처**: 전체 그림을 "브라우저 / 서버 / 현장" 3층으로, 구성 요소표와 기술 스택을 기준서 3장으로. 좌표·단위 규약(기준서 5장) 요약 절 추가. Omniverse는 V3 칸으로.
6. **05 로드맵**: 단계 1~3을 기준서 10장 일정(1주 규약 → 2~4주 머신빌더 → 5~6주 팩토리빌더 → 6~8주 시뮬 → 9~10주 리포트·최적화 → 11주 마감)으로 바꾸고, 게이트 2개를 완료 조건으로.
7. **07 용어집**: 새 용어 추가. 예: 머신빌더, 팩토리빌더, 블록, 소켓, 관절, 태그 규칙, fidelity 등급(L1 카드 / L2 기구·신호 / L3 물리), DES(이산사건 시뮬레이션), 신호 테이블, 디지털 섀도, 설비 카드, 게이트, 시나리오.
8. **08 역할**: 기준서 장별 주 담당 추가 (아래 표). RS 설명을 결정 2에 맞게 수정.

## 5. 랜딩 사이트는 어떻게 하나

기준서는 랜딩 페이지를 다루지 않습니다. 그래서 랜딩은 지금 규칙(D-05: 화면에 필요한 파일만, 빌드 도구 없음)을 유지하고, 기준서의 기술 스택(React 등)은 **적용하지 않는 예외**로 적어 둡니다.

바뀔 수 있는 것은 결정에 따라 아래 정도입니다. 지금 당장 고칠 것은 없습니다.

## 6. 주의할 점

- **일정**: 기준서의 11주는 "한 사람이 전담 + 결정 담당자가 매일 1~2시간"이 전제입니다. 병행하면 22주로 잡으라고 적혀 있습니다. 오너가 매일 확인할 시간이 가장 큰 변수입니다.
- **현장 자료**: 기준 설비 3종과 기준 공장 1개의 실제 치수·I/O 리스트가 없으면 1주차를 끝낼 수 없습니다. 미리 모아 두면 좋습니다.
- **라이선스**: realvirtual(AGPL) 코드는 참고만, 복사 금지. 메이커 CAD 파일은 라이브러리에 넣지 않음.
- **바꾸기 어려운 것**: 기준서 2장(원칙)·4장(데이터)·5장(좌표)은 첫 주에 정하면 이후 바꾸지 않는 것이 원칙입니다. 그 전에 충분히 검토해야 합니다.
- **문서 중복 방지**: 우리 문서에 기준서 내용을 길게 옮기지 않습니다. 기준서가 R2로 바뀌면 우리 문서는 링크만 고치면 되도록.
